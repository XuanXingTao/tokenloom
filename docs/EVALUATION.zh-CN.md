# 评测：先证明保真，再计算净收益

TokenLoom 0.1 首先是面向 Codex／ChatGPT 的轻量 Skill／指令文件包，可在 GitHub 分享；本地 CLI 是选配。离线 MVP 对显式输入做本地处理，提供 `count`、`compact` 和 `policy`。`compact` 默认 `safe`；`focus` 要求查询与预算，并明确属于有损选取。计数使用 `o200k_base`，不是 ChatGPT 计费接口。程序不调用模型，也不会因运行离线基准产生 API 费用。以下 API 与人工对照是后续验证方案，不是首版运行依赖或已经完成的实验。

离线结果只能说明给定样例的可见文本变短及已检查的不变量成立。它不证明模型回答质量相等、不证明 ChatGPT 订阅额度增加，也不证明实际 API 账单下降。阅读 [上游研究](RESEARCH.zh-CN.md) 时应使用同样口径。

## 1. 当前离线验证

在仓库根目录运行：

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm bench
python scripts/package.py
```

每个案例至少记录：原文、实际发送的候选文本、内容类型、模式、tokenizer 版本、前后 token、所用变换、是否有损、回退原因。基准汇总保留没有收益和负收益候选；不能只挑成功案例。

应重点审查这些边界，具体已覆盖项以测试源码和本次运行结果为准：

| 案例 | 需要验证的性质 |
|---|---|
| 短文本、不能缩短的输入 | 原样返回，不为展示压缩率而改写 |
| JSON 字符串、数值、转义、嵌套 | 区分值的保留与原始字节相同；不能默默改变数值、类型或顺序语义 |
| 数字、单位、否定、限定词 | 不因“精简”改变条件和结论 |
| 代码、命令、路径、引文 | 保持需要精确复制的字符 |
| 中文及混合语言 | 不按字符数冒充 token，不默认换语言 |
| 有损 focus | 明示省略；重要内容保留失败时不能宣称保真 |
| 很小预算 | 不截断代码或关键信息以伪装达标；无法安全满足时返回明确状态 |
| 已压缩输入、格式异常 | 不反复放大；解析不成立时保守返回 |

`safe` 是策略名称，不自动构成任意任务的正确性保证。比如将日志中重复记录合并，必须保留重复次数及必要顺序；统计、审计任务对这类信息尤其敏感。`focus` 不能用于需要遍历全部记录的计数、极值或合规证明，除非另有确定性全量计算。

## 2. 本地净 token：计入新增文字

先明确测量边界。只比较原数据与压缩数据，得到的是**片段缩短率**。若实际还需加入解码说明、输出策略或恢复提示，必须一起比较：

```text
T_base_local = tokens(基线实际发送的完整可见文本)
T_new_local  = tokens(新方案实际发送的完整可见文本)
ΔT_local    = T_base_local - T_new_local
R_local     = ΔT_local / T_base_local
```

新方案完整文本包含：压缩资料、格式说明、字段表头、来源或省略标记、附加指令，以及当次要发送的恢复说明。若 `policy` 是另外粘贴的，就把它加入新方案；不能用 `compact` 的报告代表全部开销。

应对拼接后的完整文本重新计数。BPE 在边界处的结果不一定等于各片段 token 简单相加。消息角色包装、工具 schema、服务端追加上下文、隐藏推理不在本地纯文本计数范围内。

跨多轮时，累计所有请求与输出；重发的历史在每次实际请求中都可能再次计入。恢复和重试都是该任务成本：

```text
T_task = Σ(每次请求的输入 token + 每次响应的输出 token)
ΔT_task = T_base_task - T_new_task
```

上式必须使用同一来源和同一计数定义。若 provider 的 output 总量已包含 reasoning，不能再把 reasoning 子项加一次。缓存改变价格，不意味着这些输入 token 从统计里消失。

## 3. 后续 API 三臂实验（尚未完成）

| 实验臂 | 内容 |
|---|---|
| A：原始基线 | 原资料、相同任务、无额外简洁策略 |
| B：普通简洁控制 | 原资料加一句与任务语言一致的“请简洁回答” |
| C：TokenLoom | 相同任务、实际压缩资料、实际所需说明与策略 |

B 与 C 的差异能排除单纯“要求简洁”造成的收益。若要声称胜过 Caveman，应额外增加固定版本 Caveman 臂；只运行以上三臂不能得出竞品优势。

实施要求：

1. 固定任务集、模型版本、请求参数、工具、数据快照、权限、成功条件与重试规则。随机轮换执行顺序，至少多次重复；缓存冷/热场景分开。
2. 覆盖短问答、复杂解释、中文混排、代码、日志、结构化数据、全量统计和长会话。评测集与调参集分开，禁止只用带一个异常的重复噪声数据推断所有任务。
3. 质量优先用确定性答案、执行结果和类型/数值/条件校验；开放问题进行盲审。正则命中只代表对应检查通过。
4. 有损臂允许取回原文，但统计恢复输入、恢复输出、额外轮次、失败和延迟。各臂获得的原始资料与工具权限应一致。
5. 保存脱敏原始请求、回答、provider usage、模型信息、版本、时间、失败原因和实际参数。缺失 usage 的任务不能混入“实测成本”分母。
6. 报告逐任务结果、总量与分布、任务级重复采样的置信区间，以及质量差异。预先确定质量容忍边界；没有显著差异不等于已经证明等价。

账单另算，使用测量时对应模型的官方价格和 usage 字段：

```text
C_task = Σ(各输入计费桶数量 × 对应费率 + 输出计费量 × 对应费率)
         + 计费工具及其他费用
```

输入桶可能区分未缓存、缓存读取和缓存写入，按 provider 定义处理，不能双计。不存在统一固定折扣。原始 token 总数、价格加权成本、延迟和正确率应分别展示。

## 4. ChatGPT 人工三臂实验（尚未完成）

使用相同 A/B/C 设计，分别在新建对话中提交，尽量保持所选模型、可用工具、个性化设置和时间一致。记录界面显示的模型及操作日期；不能假定 ChatGPT 界面与某个固定 API 模型完全相同。

把回答随机编号后，按任务成功、事实准确、关键条件完整、可读性评分；可额外记录可见回答的离线 token 数和人工操作耗时。续聊资料必须由用户核对，未列入的历史信息不能假定仍然存在。

ChatGPT 界面通常不足以给出完整 provider usage。本实验只能报告可见输入/输出和人工质量结果，不能把估算包装成内部总 token、真实推理 token、订阅额度或实际账单。回答变短，也可能增加追问轮次，应该把完成同一任务所需的全部轮次纳入比较。

## 发布声明门槛

- 只有离线数据：写“在这些公开样例中，可见文本 token 减少 X%”，同时附版本、样例和保真检查范围。
- 有完整 API 三臂结果：才报告对应任务集的 provider token 与价格加权成本；质量未达门槛的任务单独列出。
- 有 ChatGPT 人工结果：写可见文本和盲审结果，明确不能观测的内部量。
- 尚未直接比较当前 Caveman：不写“比 Caveman 更省”“保持所有信息”或固定节省比例。

发现新方案使相同任务的完整成本增加时，应报告负收益并关闭该场景的变换，而不是更换分母或删掉案例。
